# 核心概念

阅读本文可以让你在修改高级设置之前理解 nanobot 的运行机制。本文解释各个组成部分，无需先读源码。

如需了解源码归属和扩展点，读完本文后请阅读 [`架构说明.md`](./架构说明.md)。

## 运行时全貌

nanobot 有一个小型核心循环和几种进入方式：

| 组成部分 | 作用 |
|---|---|
| Agent 循环 | 构建上下文、选择会话、调用模型、运行工具、发布回复 |
| Provider | LLM 后端，如 OpenRouter、Anthropic、OpenAI、Bedrock、Ollama、vLLM 及其他 OpenAI 兼容 API |
| Channel | 面向用户的传输层，如 CLI、WebUI/WebSocket、Telegram、Discord、Slack、飞书、微信、邮件等 |
| Tool | 模型可调用的能力，包括文件、Shell、网页搜索/抓取、MCP、Cron、图片生成、子 Agent 等 |
| Memory | 工作区文件和会话历史，在多次对话间保留有用上下文 |
| Gateway | 常驻进程，连接已启用的渠道并暴露健康检查端点 |

最简单的路径是 `nanobot agent -m "Hello!"`：一条入站消息经过 Agent 循环，将回复打印到终端。常驻路径是 `nanobot gateway`：渠道从聊天应用或 WebUI 接收消息，发布到同一个 Agent 循环，再将回复发回来源渠道。

## Config 与 Workspace

默认实例位于 `~/.nanobot/` 下：

| 路径 | 含义 |
|---|---|
| `~/.nanobot/config.json` | 实例配置：provider、模型默认值、渠道、工具、gateway、API 和运行时选项 |
| `~/.nanobot/workspace/` | Agent 工作区：memory、session、heartbeat 任务、cron 任务、技能和生成产物 |

可以通过命令行参数覆盖：

```bash
nanobot onboard --config ./bot-a/config.json --workspace ./bot-a/workspace
nanobot agent --config ./bot-a/config.json --workspace ./bot-a/workspace -m "Hello"
nanobot gateway --config ./bot-a/config.json --workspace ./bot-a/workspace
```

config 文件控制 nanobot 可以使用什么。workspace 是 nanobot 为该实例保存状态的地方。

## 配置文件格式

`config.json` 同时支持 camelCase 和 snake_case 键名。文档中使用 camelCase，因为 nanobot 写回磁盘的配置使用 camelCase 别名，例如 `apiKey`、`modelPresets`、`intervalS`、`maxToolResultChars`。

大多数示例是局部片段。将它们合并到 `nanobot onboard` 创建的现有文件中；除非你想重置实例，否则不要替换整个文件。

## 一次 Agent 回合

正常的一次对话回合遵循以下流程：

1. 渠道收到用户消息，将其发布到消息总线。
2. Agent 循环选择会话 key，从工作区、技能、记忆、最近消息、渠道元数据和运行时设置构建上下文。
3. Provider 接收模型请求。
4. 如果模型请求工具，Runner 执行这些工具并将结果反馈给模型。
5. 最终回复保存到会话并通过渠道发回。

无论消息来自 CLI、WebUI、Telegram、Discord 还是其他渠道，这个流程都是一样的。

## CLI、Gateway、API 和 WebUI

| 入口 | 命令 | 用途 |
|---|---|---|
| CLI 单次 | `nanobot agent -m "..."` | 首次运行检查、脚本和快速本地问答 |
| CLI 交互 | `nanobot agent` | 带持久会话历史的终端聊天 |
| Gateway | `nanobot gateway` | 聊天应用、WebUI、heartbeat、Dream 和常驻服务模式 |
| OpenAI 兼容 API | `nanobot serve` | 通过 `/v1/chat/completions` 进行编程调用 |
| WebUI | `nanobot gateway` 加上 WebSocket 渠道 | 由 WebSocket 渠道在端口 `8765` 上提供的浏览器工作台 |

Gateway 健康检查端点在 `gateway.port` 上（默认 `18790`）。浏览器 WebUI 由 WebSocket 渠道提供（默认 `8765`），而非健康检查端点。

## Provider 和模型选择

当前模型通常应通过 `agents.defaults.modelPreset` 选择的命名 `modelPresets` 条目来指定。直接设置 `agents.defaults.provider` 和 `agents.defaults.model` 仍然构成旧版或最小配置的隐式 `default` 预设。当前 provider 按以下顺序解析：

1. 如果当前预设的 provider 或隐式默认 provider 不是 `"auto"`，nanobot 使用该 provider。
2. 如果 provider 是 `"auto"`，nanobot 尝试从模型名称、已配置的 API key、本地 provider 基础 URL 或 gateway provider 推断。
3. OAuth provider（如 OpenAI Codex 和 GitHub Copilot）需要显式登录并在当前预设中显式指定 provider/模型。

首次设置时，在预设中固定 provider，调试会更容易：

```json
{
  "modelPresets": {
    "primary": {
      "provider": "openrouter",
      "model": "anthropic/claude-opus-4.5"
    }
  },
  "agents": {
    "defaults": {
      "modelPreset": "primary"
    }
  }
}
```

实际示例参见 [`providers.md`](./providers.md)，完整 provider 参考参见 [`configuration.md#providers`](./configuration.md#providers)。

## Channel 和 Session

每个渠道将入站消息映射到一个会话 key，使得独立对话保持各自的历史。WebUI 还支持多个聊天和基于工作区的元数据，便于项目工作区管理。

`agents.defaults.unifiedSession` 可以有意识地在多个渠道之间共享一个会话，适用于单用户多设备场景。如果你希望不同的人、群组、渠道或项目保持独立的上下文，请关闭此选项。

## Memory、Session 和 Dream

nanobot 使用两种相关的存储：

| 存储 | 位置 | 用途 |
|---|---|---|
| Session | `<workspace>/sessions/*.jsonl` | 回放到上下文中的近期对话轮次 |
| Memory | `<workspace>/memory/MEMORY.md` 和 `<workspace>/memory/history.jsonl` | 长期事实和整合后的历史 |

Dream 是一个定期整合作业。它读取累积的历史记录并更新工作区 memory，使有用的上下文能在短暂的 session 回放之外继续保留。

详细设计参见 [`memory.md`](./memory.md)。

## Tool 和安全

工具从内置模块和插件入口点自动发现。常见工具组包括：

- 文件读写/编辑和补丁；
- 带可配置沙箱的 Shell 执行；
- 带 SSRF 检查的网页搜索和抓取；
- MCP 服务器；
- Cron 提醒和 heartbeat 任务；
- 图片生成；
- 子 Agent 和运行时自省。

安全相关控制见 [`configuration.md#security`](./configuration.md#security)。对于生产环境或共享聊天应用，还需配置渠道访问控制，如 `allowFrom`、配对码或 WebSocket token。

## 后台任务

启动 `nanobot gateway` 时，它会在 `<workspace>/cron/jobs.json` 创建工作区级别的 cron 存储，并注册系统任务：

- `dream`，当 `agents.defaults.dream.enabled` 为 true 时；
- `heartbeat`，当 `gateway.heartbeat.enabled` 为 true 时。

Heartbeat 读取 `<workspace>/HEARTBEAT.md`。如果文件中有 `## Active Tasks` 标题下的任务，nanobot 会执行它们并将有用结果发送到最近活跃的聊天目标。

用户创建的提醒使用同一个 cron 服务，但与受保护的 heartbeat 系统任务不同。
